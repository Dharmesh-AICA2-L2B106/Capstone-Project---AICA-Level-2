Stage 5.2 - connect to the engine. Build Guide 5.2: Create a server-side function "engine-proxy" that forwards authenticated requests to ENGINE_URL with the user's token, so no keys reach the browser. Remove mock data, add loading and error states, and log each call to audit_log.

Details (keep everything built so far; change only what is needed):

A. Edge function engine-proxy (Supabase)
- Secret ENGINE_URL = https://auditsmart-engine.onrender.com (add it as a secret, never in code).
- The browser calls {SUPABASE_URL}/functions/v1/engine-proxy/v1/<path>?<query> with the user's access token. The function verifies the user is signed in (supabase.auth.getUser with that token; otherwise 401 JSON {"detail":"Please sign in again."}).
- Allow only paths starting with /v1/ (otherwise 400). Forward method, path, query and body unchanged to ENGINE_URL, with Authorization: Bearer <the same user access token>. Send no other keys. Do not forward cookies or the apikey header.
- Pass bodies through as raw bytes: JSON, multipart/form-data (keep the boundary in Content-Type), application/octet-stream chunks (PUT /v1/uploads/{id}/chunks/{n}), and binary responses (GET /v1/workpapers/{id}/file is an xlsx; keep Content-Type and Content-Disposition). Never parse or re-encode file bodies.
- Return the engine's status code and body unchanged (including 4xx/5xx JSON {"detail": ...}). Handle CORS (OPTIONS; expose Content-Disposition).
- Timeout about 90 s per attempt. On 502, 503 or 504 (Render free plan is asleep), wait 5 s and retry once; stay under the 150 s function limit. A timeout returns 504 {"detail":"Engine is waking up (about a minute). Please try again."}.
- After each call, insert one audit_log row with the service role (server side only): action "engine_call", entity "engine", user_id, firm_id from the token, new = {method, path (no query string), status, duration_ms, engagement_id}. engagement_id comes from the path /v1/engagements/{id} or from the request header x-engagement-id (sent by engine.ts, not forwarded). Never log request or response bodies, file names, client names or tokens. A logging failure must not fail the call.

B. src/lib/engine.ts
- Every engine call goes only through engine-proxy (one helper: engineFetch(method, path, {query, json, form, bytes, engagementId})). No direct calls to the engine URL from the browser.
- Remove all mock data and mock switches. Every screen that uses engine data gets a loading state, an error state and an empty state.
- Show engine errors verbatim (the "detail" text; for 422 list each item's msg). If a call takes more than 5 s, show "Engine is waking up (about a minute)" with a spinner.
- Downloads (workpaper xlsx): fetch through the proxy as a blob and save it; file_url from the engine is a /v1/ path for the proxy.
- Footer and version come from GET /v1/health.

C. Roles and firm into the token (SQL migration)
- The engine reads roles only from app_metadata.roles and the firm only from app_metadata.firm_id. Role names must be exactly: Admin, Partner, Manager, Senior, Staff, TaxPartner.
- Create a SECURITY DEFINER function (search_path = public) that, for one user, writes raw_app_meta_data = raw_app_meta_data || {"roles": [...], "firm_id": "..."} into auth.users from the table(s) where we keep user roles and firm assignment (e.g. user_roles / profiles). Map variants to the exact names (tax_partner, tax partner, taxpartner -> TaxPartner; admin -> Admin; etc.). A user with no firm (platform Admin) has firm_id removed.
- Add triggers (after insert, update, delete) on the roles table and on the firm assignment that call it. Run a one-time backfill for all existing users. Keep the RLS helpers current_firm_id() and has_role() working.
- Users must sign out and in again to get a new token; show that hint after a role change.

D. Engagement sync (the engine needs the same engagement, client and team)
- Whenever an engagement or its team is created or edited (and when a client is edited, for each of its engagements), call PUT /v1/engagements/{engagement.id} with exactly this body:
  {"client":{"id":"<clients.id>","client_code":"<code>","name":"<name>","emirate":"<Dubai|Abu Dhabi|Sharjah|Ajman|Umm Al Quwain|Ras Al Khaimah|Fujairah>","entity_type":"<or null>"},
   "fye":"YYYY-MM-DD","framework":"<or null>","materiality":"1500000.00","perf_materiality":"1125000.00","trivial":"75000.00","status":"<status>",
   "members":[{"user_id":"<auth user id>","role":"Manager"}]}
- Use the same Lovable uuids for the engagement id and the client id. Money as strings with 2 decimals (or null). user_id is the Supabase auth user id (the token sub). members is the whole team (the engine replaces it); it must contain at least one Manager or Partner, each user once, roles with the exact names above.
- 201 = created, 200 = updated. On an error, keep the Lovable save, show the engine's message and a "Not synced - Retry" badge on the engagement; retry calls the same PUT.
- When the platform Admin creates a firm, also call POST /v1/firms {"id":"<firms.id>","name":"<name>"} (409 = already registered, treat as success).
- One-time admin actions on Admin: platform Admin "Register all firms in engine" (POST /v1/firms for each firm; 409 = OK). Firm Admin "Sync all engagements" (PUT for every engagement of the firm, one at a time, with a progress count and a list of failures with the engine's message). The engine refuses a firm that is not registered yet (403), so register firms first.

E. Audit log: as in A, one row per engine call; no bodies or client names.

F. Settings/Admin: an "Engine status" card that calls GET /v1/health and shows status, version, environment, db and queue, the time of the check, and a Refresh button (waking-up state as in B).

G. At the end, report to me in the chat: (1) which table holds user roles and how firm_id is stored per user; (2) the JWT algorithm from the access token header only (alg and kid if present, e.g. HS256 or ES256); do not print the token or any secret; (3) the list of files changed.

## If something fails
- **401 from the engine:** token not accepted – check AUTH_PROVIDER / issuer / JWT alg (step 2).
- **403 "not linked to a firm":** the user has no `app_metadata.firm_id` → sign out/in; check the trigger.
- **403 "not registered in AuditSmart yet":** run "Register all firms in engine" (platform Admin).
- **409 "not linked to a firm" on sync:** an old engine-only client (e.g. DUMMY01) – ignore, or link it via `PUT /v1/firms/{firm}/clients/{id}`.
- **422 on sync:** the message names the field (e.g. no Manager/Partner in the team, perf > materiality).
- Note: Render's free disk is ephemeral – uploaded datasets and workpapers disappear after a
  restart or sleep; the engagements stay (Postgres). Re-run "Sync all" is never needed for
  that, but datasets must be uploaded again.
